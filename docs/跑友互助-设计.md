# 跑友互助（赛事互助板）设计方案

> 状态：**设计稿，未开发**。先过一遍方案，确认后再动手。
> 适用版本：V2.9

---

## 1. 它是什么

挂在**某一场具体赛事**下面的、有**明确截止时间**的跑友互助信息。

典型场景：跑外地马拉松要住宿，想找个拼房搭子分摊房费；想拼车去起点或一起领物；想约同城跑友赛前吃个饭。

一句话：**赛前的、临时性的、围绕一场比赛的 mutual help，用完即消失。**

## 2. 它不是什么（这条最重要）

| 不做 | 原因 |
|---|---|
| ❌ 帖子 / 动态 / 信息流 | 那就是社区论坛，个人主体做不了，会审不过 |
| ❌ 评论、回复、盖楼 | 一旦有二级互动就是 UGC 社区 |
| ❌ 点赞、关注、粉丝 | 社交关系链，红线 |
| ❌ 平台内聊天 / 私信 | 属于即时通讯类社交功能 |
| ❌ 在线支付、担保交易、抽成 | 个人主体开不了微信支付，且一旦碰钱责任说不清 |
| ❌ 房源发布 / 酒店预订 | 需要相应类目资质，我们不碰，只做"人找人" |
| ❌ 二手闲置买卖、寄送 | 哪怕说"免费送"，一旦走邮寄就容易变成灰产（付邮骗局），也容易踩二手类目。只允许赛事现场当面交付 |

**和已有功能的关系**：赛事已经有「交流群」二维码。群是长期的、需要管理员建；互助是赛前临时的、跑友自己发。两者互补，互助成功后通常就进群了。

---

## 3. 合规边界：怎么避开"社区/论坛"的认定

微信对个人主体小程序的核心限制是不允许经营性质/UGC 社区内容。我们的设计用四条把边界锁死：

1. **强绑定赛事**：每条互助必须挂在某一场赛事下，不存在"全站信息流"，也不做列表页推荐。看不到"别人的动态"，只能看到"我关注的这场比赛下有什么"。
2. **限时**：必填截止时间，最长到赛事结束后 3 天，到点自动归档（不可见）。内容不沉淀。
3. **限量**：每人每场赛事最多 3 条，每天最多发 5 条。不形成内容沉淀。
4. **无互动**：没有评论、没有点赞、没有回复。想联系就"应征"，走线下。

另外，命名上避开敏感词：界面统一用「互助」「应征」，**不出现**「社区」「广场」「圈子」「论坛」「帖子」「动态」。

### 送审策略（建议）
- 首次提交只带核心功能（发布 / 应征 / 我的），做小版本试审，看审核意见再迭代。
- 如果被判"信息发布类"，退路是：加**邀请门槛**——只有进了该赛事交流群的跑友才可发（复用现有群成员标记），把开放发布收成半私域。

## 4. 隐私保护：联系方式怎么给

这是整个功能最容易出事的地方。明文把手机号挂在页面上，等于公开贩卖隐私，平台要担责。

**方案：联系方式双向按需披露（推荐）**

```
公开状态：所有人看到的互助条目里，没有任何联系方式
              ↓
浏览者点「我来应征」，填自己的联系方式 + 一句留言（提交后不可修改/他人不可见）
              ↓
双方互见：应征成功后，发布者和该应征者互相看到对方的联系方式
              ↓
线下自行联系加微信，平台不介入
```

要点：
- **只收微信号，不收手机号**（V2.9 确定）。手机号能直接拨号、可被反查到一堆账号、泄漏了还改不了；法律上属于敏感个人信息，一旦采集就要在隐私协议里单独声明并承担保管责任。微信号的处置成本低，用户可以随时拉黑、随时换。所以平台**根本不采集手机号**，库里也没有这个字段。表单里写死一句提示，告诉跑友为什么。
- **应征可以撤销，同一场赛事上限 3 次**（V2.9 确定）。只限制"取消次数"挡不住薅联系方式的人——撤销照样把微信号拿到了。所以做成闭环：**撤销满 3 次后，本场赛事既不能取消，也不能再应征任何互助**（相当于 12306 退票多了限制购票，而不是只限制退票）。按钮上直接写"还剩 N 次"，用完变灰，丑话说在前面。
- **浏览不要钱不要门槛，但索取联系方式必须付出同等诚意**（你自己也要填）——这条能有效挡掉薅联系方式的人。
- 联系方式全程**不出现在公开接口返回里**，云函数按身份裁剪字段。
- 提供「一键清除我的联系方式」：用户在个人资料页可以把已提交的联系方式从所有应征记录里抹掉。
- 号码不作展示样式处理（不自动识别拨号），纯文本呈现，避免被抓取。
- 建议加**每日查看上限**：同一个用户每天最多查看 N 个联系方式（防批量采集）。

> 备选（不推荐）：明文展示联系方式。简单，但泄露风险和平台责任都高，不建议。

## 5. 用户流程

### 发布
```
赛事详情页 →  🙌 跑友互助 卡片 →  「发布互助」
  → 填：类型 / 标题 / 说明 / 费用(AA 说明) / 需要几人 / 截止时间 / 我的联系方式
  → 勾选免责声明（必选）
  → 内容安全检测（文本）
  → 发布成功，出现在该赛事互助列表里
```

门槛：**必须已关注该赛事**（已有关注数据）才能发布和应征，避免无关人等和机器人。

### 应征
```
点开某条互助 → 看说明/费用/截止时间 → 「我来应征」
  → 填联系方式 + 留言 → 提交
  → 双方互见联系方式，自行联系
```

发布者在「我发布的」里能看到应征者列表（含联系方式）和留言，可以一键复制，也可以「结束招募」。

### 结束 / 过期
- 手动关闭（找到人了）／截止时间到／赛事结束 → 自动 `closed`，从列表消失，进「历史」。
- 每天凌晨定时跑一遍把过期的关掉。

### 举报
条目详情 → 「举报」→ 累计 3 次自动下架并通知管理员。管理员在后台可以看到待处理的举报。

## 6. 数据结构

### 集合 `race_helps`（互助条目）
| 字段 | 类型 | 说明 |
|---|---|---|
| `_id` / `_openid` | | 自动 / 发布者 openid |
| `eventId` | string | 所属赛事 |
| `userId` / `nickName` / `avatarUrl` | string | 发布者快照 |
| `type` | string | `room` 拼房 / `carpool` 拼车 / `expo` 领物同行 / `gear` 装备互借 / `give` 装备赠送 / `other` 其他 |
| `title` | string | 标题，≤ 20 字 |
| `desc` | string | 说明，≤ 200 字 |
| `costNote` | string | 费用说明，纯文本，如「AA，预计 200/晚」 |
| `peopleNeeded` | number | 还差几人，1-9 |
| `deadline` | Date | 截止时间 |
| `contact` | object | `{ wechat, phone }` **绝不返回给无关用户** |
| `status` | string | `open` / `closed` / `canceled` / `banned` |
| `applyCount` | number | 应征人数 |
| `reportCount` | number | 举报次数 |
| `disclaimerAgreed` | boolean | 是否勾选免责 |
| `createTime` / `updateTime` | Date | |

### 集合 `race_help_applies`（应征记录）
| 字段 | 说明 |
|---|---|
| `helpId` / `eventId` | 关联 |
| `userId` / `nickName` | 应征者 |
| `contact` | `{ wechat, phone }` 仅发布者可见 |
| `message` | 留言，≤ 50 字 |
| `status` | `pending` / `accepted` / `canceled` |
| `createTime` | |

**索引**：`eventId + status + deadline`（列表）、`userId + createTime`（我的）。

> **首版范围（V2.9）**：只做 `room` / `carpool` / `meal` 三种。装备互借、赠送暂不做——
> 涉及物品就有估值、损毁、交付纠纷，平台说不清，等跑顺了再看。
> 云函数 defend TYPES 白名单里也没给这两个留口子，前端不放、后端也不会收。

**留存**：过期满 30 天定时物理删除，联系方式不留历史。

## 7. 云函数

新增 **`raceHelp`**（`cloudfunctions/raceHelp`，Nodejs16.13），action：

| action | 说明 | 关键校验 |
|---|---|---|
| `list` | 某赛事下开放的互助列表 | 已登录；自动过滤过期/下架；**不返回 contact** |
| `detail` | 单条详情 | 同上；仅本人/发布者可见联系方式（且需已应征） |
| `create` | 发布 | 登录 + 已关注该赛事 + 内容安全 + 频率限制 + 免责勾选 |
| `apply` | 应征 | 登录 + 已关注 + 不能对自己 + 不重复应征 |
| `applicants` | 我收到的应征列表 | **仅发布者本人**可调 |
| `myHelps` / `myApplies` | 我发布的 / 我应征的 | 本人 |
| `close` | 关闭/取消 | 仅发布者 |
| `report` | 举报 | 一人一条一次；≥3 自动 `banned` |

安全项：
- **内容安全**：`security.msgSecCheck`（云调用）+ 敏感词兜底词典，不通过直接拒绝并提示。需在函数 `config.json` 声明对应开放接口权限。
- 音频：文本 → `msgSecCheck`；后续若允许配图 → `imgSecCheck`。**首期不放图片**，少一半麻烦。
- 频率：每人每赛事最多 3 条 open、每天 5 条；应征每天上限 10 次。
- 输入长度、类型白名单严格校验（防注入/绕过）。

### 定时
新增一个清理任务（可并入现有的 `raceQrExpireNotify` 定时，或单独 `raceHelpClean`）：每天把 `deadline < now` 的置为 `closed`，并把过期 30 天的数据物理删除。

### 8.2 「我的」里的入口
复用现有 tab 结构：在跑马记录旁边或「我的」列表加一行「🙌 我的互助」，内页两个 tab：**我发布的**（可关闭/查看应征者）、**我应征的**（可取消）。

### 8.3 管理后台 `pages/admin/races`
参照已心愿单的做法：加「🙌 互助管理」入口 → 列表（可按赛事/状态筛）→ 下架（banned）/恢复 / 查看举报详情。

### 8.4 分享
分享仍以**赛事**为单位，不做单条互助的分享卡片——避免变成对外传播的内容载体。

## 9. 免责设计（贯穿全链路）

1. **发布前强制勾选**（不勾不能提交）：
   > 我确认：本条信息由我个人发布，平台仅提供展示，不参与撮合、不代收款项、不承担任何纠纷责任。我已知悉平台无法核实他人身份，线下接触请自行判断风险。

2. **列表常驻一行小字**：
   > 信息由跑友自发发布，平台不收费、不审核真实性、不负责协调

3. **应征前二次确认弹窗**：提示对方身份未经核实，注意人身与财产安全，建议群内公开沟通。

4. **详情页固定免责块**（不可关闭）。

5. **个人资料页**提供「清除我提交的联系方式」按钮。

## 11. 待确认

1. **联系方式披露方式**：是否采用第 4 节的"应征后互见"？（推荐，但比明文多一步操作）
2. **类型范围**：已确认只做拼房 / 拼车 / 约饭三种。装备互借与赠送都不做（见第 6 节"首版范围"），理由是涉及物品就有估值、损毁、交付纠纷，平台说不清。
3. **发布门槛**：是否需要"已关注该赛事"才能发布？（推荐要，能挡机器人）
4. **审核策略**：先做小版本试审，还是稳妥起见先上"仅群成员可发布"的半私域版本？
