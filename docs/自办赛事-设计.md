# 自办赛事（跑团自己办的比赛）设计方案

> 状态：需求已定稿，**未开发**。2026-11-04 修订（加入线上赛形态）
> 决策来源：与产品负责人的六轮确认（见第 3 节）

---

## 1. 它是什么

管理员在小程序里发起一场**自己办的比赛**，两种形态共用一套流程：

- **线下赛**：固定时间、固定集合点，现场跑，管理员现场盯
- **线上赛**：给一个时间窗口，参赛者在窗口内自己找时间地点跑完，提交成绩 + 截图，管理员审核

两种形态都走「关注 → 报名 → 完赛 → 成绩」这条主线，报名费线下收、线上只标记，**意外险由管理员统一代买**（报名即收集投保信息）。

一句话概括：**借用现有赛事体系的外壳，补上「报名管理」「成绩提交与审核」两段。**

## 2. 它不是什么（边界，先划清）

1. **不是报名平台**：不接支付、不代收钱、不开票。收钱是跑团内部线下的事，小程序只留一个「已收款」的勾。
2. **不是计时系统**：没有芯片、没有分段计圈。线下靠现场、线上靠截图，成绩都要人看。
3. **不是保险代售渠道**：不卖保险、不代收保费（没有资质）。只负责**收集投保信息、登记保单号**，实际投保由管理员线下找保险渠道完成。
4. **不是对外开放的赛事发布**：只有管理员能发起，普通成员只能报名。
5. **不是新的一套赛事表**：自办赛就是 `race_events` 里的一条，靠 `source` + `mode` 区分。

## 3. 已定决策

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 谁能发起 | **仅管理员**，普通成员无入口 |
| 2 | 支付 | **不做**。线下收款，管理员在名单里勾「已收款」 |
| 3 | 赛事怎么进系统 | 赛事管理里新增，`source='self'`；用户**正常关注**，共用日历/详情/评价/互助 |
| 4 | 报名资格 | **必须是小程序注册成员**（`users` 表里存在的账号） |
| 5 | 线下赛成绩 | 本人标记完赛后录入，进「我的跑马记录」，**计入 PB** |
| 6 | **线上赛形态** | **支持**。`mode='online'`：时间窗口内自跑，提交成绩 + 截图 |
| 7 | **线上成绩审核** | **必须管理员审核**，通过后才进记录、才进榜单；驳回要写理由 |
| 8 | **意外险** | **管理员统一代买**（团险）。报名时收集投保信息（姓名/证件号/手机），线下投保后回填保单号。**不做「自购 + 传图」**——会有人偷懒、拿别人的图 |
| 9 | 退赛 | **允许**。`status='quit'`，不删记录，保留缴费痕迹 |
| 10 | 删除赛事 | 0 人报名 → 直接删；有人报名 → **二次确认**（级联清报名，**保留跑马记录**） |
| 11 | 组别 | 选填（线上赛建议必填，否则没法排名） |
| 12 | 退赛是否记「已退费」 | 不做，备注里写 |
| 13 | 报名截止后管理员代报 | 允许 |
| 14 | 线上成绩计入 PB | **默认不计**（无人见证，怕刷榜）。记录带「线上」标记，要改说一句 |

## 4. 两种形态的差异

| 维度 | 线下赛 | 线上赛 |
|---|---|---|
| 时间 | 固定日期时间，统一发枪 | `runWindow` 开窗期间任意时间完成 |
| 地点 | 固定起点，集合信息 | 自己定，可选「推荐路线」 |
| 签到 | 二维码扫码签到 | 无签到，**提交成绩即视为完成** |
| 成绩 | 本人录入，现场有见证 | 提交成绩 + 截图/轨迹，**待审核** |
| 审核强度 | 抽查（管理员看着现场） | **全量审核**，一条不漏 |
| 排名 | 可选 | **必须有成绩榜**（线上赛的核心产出） |
| 保险 | 管理员统一代买，报名即收集投保信息 | 同上；窗口期可能跨多天，保单要覆盖整个窗口 |
| 人数上限 | 有（场地限制） | 有，但可以放得很宽 |
| 报名费 | 常见 | 常见免费 |

## 5. 用户流程

### 5.1 管理员发起

```
赛事管理 → 新建/编辑赛事 → 勾「自办赛事」→ 选形态（线下 / 线上）
  ├ 基础信息：名称、日期、城市、路线图、海报 —— 和现有表单一致
  ├ 报名设置：人数上限、报名截止、报名费说明、组别
  ├ 线下专属：集合时间地点
  ├ 线上专属：跑步窗口（起止）、成绩提交截止、是否要求截图
  ├ 免责与保险：免责声明全文、保险方式（统一代买 / 自行购买 / 不涉及）、投保截止
  └ 保存 → 进赛事日历，`source='self'`，`mode` 记下形态
```

### 5.2 成员报名

```
赛事详情页（自办赛）→ 点「我要报名」
  ├ 未登录        → 跳登录
  ├ 非注册成员    → 「仅限本团成员报名」
  ├ 已满 / 已截止 → 按钮置灰，文案说明原因
  ├ 已报名        → 「已报名 · 待缴费 / 已确认」
  └ 正常          → 弹报名表单：组别、紧急联系人
                   → 投保信息：真实姓名、证件号、手机号（管理员统一投保用，必填）
                   → 单独勾选：同意为投保提供上述信息（不能和免责捆一起）
                   → 勾选免责声明
                   → 写 marker(status=registered, paid=false, insuredStatus='pending')
                   → 申请「报名成功」订阅消息
```

### 5.3 线下：收款与签到

```
报名名单页 → 勾「已收款」→ marker.paid = true
比赛日 → 扫赛事二维码签到 → marker.checkInAt
        （没扫码的由管理员在名单里手动勾）
```

### 5.4 线下：完赛录成绩

```
用户点「我已完赛」→ 确认 → 弹「录入成绩」
  ├ 成绩：时:分:秒（必填）
  ├ 组别名次（选填）、照片（选填）
  └ 跳过 → 状态 finished，记录标「成绩待补」

写入 race_records（source='self', raceMode='offline'）
  → marker.recordId 回填 → 进「我的跑马记录」，计入 PB
```

### 5.5 线上：完赛提交 + 审核

```
时间窗口内跑完 → 详情页「提交成绩」
  ├ 跑步日期（默认今天，可选窗口内其他天）
  ├ 距离 + 用时 → 自动算配速并显示
  ├ 截图（必传，1-3 张：跑步 App 记录页 / 轨迹图）
  ├ 备注（选填，如「跑步机，坡度 2」）
  └ 提交 → 写 race_result_submits(status='pending')

管理员审核（审核页逐条过）
  ├ 通过 → 写 race_records（raceMode='online'）+ 进榜单 + 发积分
  ├ 驳回 → 写理由，作者可在截止前改一次再提交
  └ 超时未提交 / 未通过 → 视为未完成，不发积分

作者可在「我的成绩」里看到：待审核 / 已通过 / 已驳回（附理由）
```

### 5.6 退赛

```
选手 → 我的报名 → 退赛 → 二次确认
  → status='quit', quitAt=now，名额释放
  → 已缴费用线下协商退还（线上赛一般不涉及）
```

### 5.7 删除赛事

| 情况 | 行为 |
|---|---|
| 报名人数 0 | 直接删 |
| 报名人数 ≥ 1 | 二次确认：**「已有 5 人报名、2 人完赛。删除后报名记录、成绩提交一并清除，跑马记录会保留。」** |

## 6. 状态机

### 6.1 报名记录（`race_markers`）

| status | 含义 | 谁改 | 占名额 |
|---|---|---|---|
| `registered` | 已报名 | 用户 / 管理员代报 | 是 |
| `quit` | 已退赛 | 用户 / 管理员 | 否 |
| `finished` | 已完赛 | 用户 | — |
| `dns` | 弃赛（报了没来 / 窗口内没提交） | 用户 / 管理员 | — |

缴费与状态独立：`paid=false` 显示「待缴费」，`paid=true` 显示「已确认」。

> `quit` 是新状态。状态文案在几处是写死的 if-else（赛事详情、成员管理 `statusName`、我关注的赛事），要一处不漏。

### 6.2 线上成绩提交（`race_result_submits`）

| status | 含义 | 后续动作 |
|---|---|---|
| `pending` | 待审核 | 管理员处理 |
| `approved` | 已通过 | 写 `race_records`，进榜单 |
| `rejected` | 已驳回 | 作者可改一次；再驳即锁定 |

### 6.3 赛事（`race_events.status`，仅自办赛）

`open` 报名中 / `closed` 截止或满员（读时判定）/ `finished` 已结束 / `cancelled` 已取消

## 7. 数据结构

### 7.1 `race_events` 新增

| 字段 | 类型 | 说明 |
|---|---|---|
| `source` | string | `self` / `official`，**老数据缺省 official** |
| `mode` | string | `offline` / `online`，仅 `source=self` 时有效 |
| `capacity` | number | 报名上限，0/空 = 不限 |
| `signupDeadline` | Date | 报名截止 |
| `feeNote` | string | 报名费说明，纯文本 |
| `groups` | array | 组别，如 `['10km','半马']` |
| `healthNotice` | string | 免责声明全文 |
| `insuranceMode` | string | `group` 管理员统一代买（默认）/ `self` 自行购买 / `none` 不涉及 |
| `meetInfo` | string | **线下**：集合时间地点 |
| `runWindow` | object | **线上**：`{ start, end }` 可跑步的时间段 |
| `resultDeadline` | Date | **线上**：成绩提交截止 |
| `proofRequired` | boolean | **线上**：是否必须上传截图，默认 true |
| `rankEnabled` | boolean | 是否出成绩榜，线上默认 true |

### 7.2 `race_markers` 新增（仅自办赛写入）

| 字段 | 说明 |
|---|---|
| `paid` / `paidAt` / `paidNote` | 线下收款标记 |
| `checkInAt` | 线下签到时间 |
| `group` | 报名组别 |
| `emergencyContact` | 紧急联系人 |
| `noticeAgreed` | 免责勾选 |
| `insuranceId` | 关联 `race_insurances._id`，**这张表不放任何证件号** |
| `insuredStatus` | `pending` 待投保 / `insured` 已投保 / `excluded` 不承保（超龄等） |
| `quitAt` | 退赛时间 |

> **为什么证件号不放在这里**：`race_markers` 现在被前端**直连查询**（`db.collection('race_markers')`，至少三处页面在用）。云开发的集合权限通常是「所有用户可读」，证件号一旦写进这张表，就等于对所有登录用户开放。所以投保信息单独建表，只允许云函数访问（见 7.5）。

> ⚠️ `race_markers.userId` 存的是 `users` 表内部 `_id`，不是 openid。这个坑已经踩过两次，新代码一律走双查。

### 7.3 `race_result_submits`（新集合，线上赛成绩提交）

| 字段 | 说明 |
|---|---|
| `eventId` / `userId` / `group` | 关联与组别 |
| `runDate` | 实际跑步日期（须落在 `runWindow` 内） |
| `distanceKm` | 距离，与组别匹配 |
| `result` | 秒数（存储），界面显示 `h:mm:ss` |
| `paceText` | 提交时算好的配速，便于审核 |
| `proofImages` | 截图 fileID 数组，1-3 张 |
| `note` | 选手备注 |
| `status` | `pending` / `approved` / `rejected` |
| `reviewerId` / `reviewNote` / `reviewTime` | 审核痕迹，**驳回必须写理由** |
| `retryCount` | 被驳回后重提次数，上限 1 |
| `createTime` | |

**索引**：`eventId + status`（审核列表）、`userId + eventId`（查重）。

> 单独建表而不直接写 `race_records`，是为了**不让未审核的成绩污染跑马记录**——审核通过才写记录，避免出现「记录里有一条待审核的假成绩」。

### 7.4 `race_records` 新增

| 字段 | 说明 |
|---|---|
| `source` | `self` / `official` |
| `raceMode` | `offline` / `online`（线上记录在列表里标「线上」） |
| `eventId` / `eventName` | 回链 + 冗余（赛事删了仍能显示） |
| `submitId` | 关联审核单，防重复写入 |

**PB 计算处**：过滤 `raceMode !== 'online'`，并在记录卡片上写「线上 · 不计入 PB」。

### 7.5 `race_insurances`（新集合，投保信息专用）

**这张表前端永远不可读**，只走云函数。集合权限设为「仅管理员端可写、客户端不可读」。

| 字段 | 说明 |
|---|---|
| `eventId` / `userId` | 关联 |
| `name` | 真实姓名（明文，投保必需） |
| `phone` | 手机号（明文，投保必需） |
| `birth` | 出生日期，用于年龄校验 |
| `idNoEnc` | 证件号**密文**：`v1.base64(iv).base64(tag).base64(cipher)` |
| `idLast4` | 证件号后 4 位，**明文**，用于列表脱敏展示 |
| `idHash` | `sha256(证件号 + 服务端盐)`，用于查重（同一人重复报名），不可逆 |
| `status` | `pending` / `insured` / `excluded` |
| `policyNo` / `insuredAt` | 保单号、投保时间 |
| `purgeAt` | 计划清理时间（活动结束后 30 天） |
| `createTime` | |

**为什么不存明文，也不只存密文**：

- 只存明文 → 数据库一旦被人拿到（或权限配错）就全泄露
- 只存密文 → 每次列表都要解密，反而扩大解密次数
- 明文姓名/手机留给人看，**证件号只存密文 + 后 4 位 + 哈希**，列表展示用后 4 位拼出来即可

## 8. 云函数

新增 **`raceEvent`**（`cloudfunctions/raceEvent`，Nodejs16.13）。

| action | 说明 | 关键校验 |
|---|---|---|
| `create` / `update` | 建/改自办赛 | 仅管理员；线上必须填 `runWindow` 与 `resultDeadline` |
| `cancel` / `delete` | 取消/删除 | 仅管理员；删除走级联（见下） |
| `signup` | 报名 | 登录 + 在 `users` 表 + 未截止 + 未满 + 未报过 + 两个勾选 |
| `quit` | 退赛 | 本人或管理员 |
| `markPaid` / `checkIn` | 线下标记 | 仅管理员 / 本人扫码 |
| `listSignups` | 报名名单 | 仅管理员 |
| `submitResult` | 线上提交成绩 | 窗口内 + 未重复提交 + 截图 + **机械校验**（第 10 节） |
| `reviewResult` | 审核 | 仅管理员；通过才写 `race_records`；驳回必须带理由 |
| `onlineRank` | 线上成绩榜 | 按组别 + `result` 升序，只列 `approved`，**实时算不落库** |
| `myResults` | 我的提交 | 本人，含驳回理由 |
| `saveInsured` | 回填保单号、标记已投保 | 仅管理员；只写 `insuredStatus`/`policyNo`，**不回传证件号明文** |
| `exportInsured` | 导出投保名单 | 仅管理员；临时解密 + 写导出日志；一次一用不落盘 |
| `purgeInsurances`（定时） | 到期清理证件号 | 每日跑；只清 `idNoEnc`，保留姓名/后 4 位/保单号 |

**删除级联（顺序不可乱）**：

```
1. race_helps / race_help_applies（互助、应征） → 物理删
2. race_reviews（评价）                        → 物理删
3. race_result_submits（线上成绩提交）          → 物理删
4. race_insurances（投保信息，含证件号密文）    → 物理删  ← 敏感数据，必须清
5. race_markers（报名/关注）                   → 物理删  ← 不删就是孤儿记录
6. race_records                               → **绝对不删**
7. race_events                                → 删除
```

## 10. 审核规范（线上赛的重点）

「审核时候要注意」——这条要落成规则，不能靠感觉。分两层：**机器先挡，人再看**。

### 10.1 服务端机械校验（提交时就挡掉明显不可能）

| 检查 | 规则 |
|---|---|
| 时间窗口 | `runDate` 落在 `runWindow` 内；提交时间 ≤ `resultDeadline` |
| 距离匹配 | `distanceKm` 与所选组别一致（10km 组不能交 5km） |
| 成绩下限 | 10km ≥ 22:00、半马 ≥ 55:00、全马 ≥ 115:00（低于即异常） |
| 配速下限 | > 150 秒/公里（即 2:30/km）直接拒 |
| 成绩上限 | 与距离不匹配的离谱值（如全马 9 小时但距离 42km 明显不符配速）提示核对 |
| 截图必传 | `proofRequired` 为真时，0 张直接拒 |
| 图片查重 | 同一 `fileID` 已在其他提交里出现 → 标记「疑似复用」，强制人工看 |
| 一人一条 | 同赛事已有 `approved` 的不能再交；`pending` 的重复提交覆盖旧的 |
| 重提次数 | 被驳回最多改一次，`retryCount > 1` 锁定 |

### 10.2 人工审核看什么（管理员必须逐条过）

1. **截图有没有关键信息**：日期、距离、用时、配速、账号昵称（App 水印）
2. **是不是跑步机/器械**：赛制若只认户外，截图里出现跑道显示、坡度、器械名要驳回
3. **有没有 GPS 轨迹**：纯数据截图容易 P，有轨迹图的优先采信
4. **有没有拼接痕迹**：字体不一致、数值与进度条不符、状态栏被裁
5. **和自己的历史比**：平时半马 1:50，这次 1:05 → 一律驳回，不管截图多干净
6. **同一天多场**：查该用户是否在别的赛事也提交了同日成绩
7. **驳回必须写理由**：一句话说清（「截图无日期」「配速异常」），作者才知道改什么

### 10.3 审核的心态

> 榜单上出现一条假成绩，整场比赛的公信力就没了。**宁可慢一天出榜，不要放过明显不可能的成绩。**

线下赛可以抽查（现场有见证），线上赛**全量审核**，一条不漏。

## 11. 意外险：管理员统一代买

### 11.1 为什么不做「自购 + 传图」

这条路的问题不在技术，在人：

- 有人嫌麻烦不买，报名时随手勾一下
- 有人拿别人的保单截图，或者从网上搜一张
- 管理员要逐张核对「这张是不是本人的、日期对不对、险种赔不赔跑步」，工作量比买保险本身还大
- 就算都核了，出险才发现保单不覆盖马拉松，前面全白干

**统一代买把责任收回到组织方**：报名就收信息，名单定了统一投，谁没投保一眼可见，不用赌人的自觉。

### 11.2 流程

```
报名 → 填投保信息（姓名 / 证件号 / 手机号 / 出生日期）
     → marker.insuredStatus = 'pending'
报名截止 → 名单锁定，管理员导出投保名单
         → 线下找保险渠道投保（按人天，通常 3-10 元/人）
         → 回填保单号 → insuredStatus='insured', policyNo
赛前 1 天 → 检查还有谁 pending（未投保不许参赛）
出险     → 选手在「我的保单」里看到保单号，直接报案
```

### 11.3 证件号怎么存（「要妥善保存」的落地）

这是整个功能里**唯一有法律风险**的部分。

**先说三条红线**：

1. **不存明文**，数据库里只有密文 + 后 4 位 + 哈希
2. **不进可被客户端直读的集合**（`race_markers` 就是这种表，所以单独建 `race_insurances`）
3. **不进日志、不进错误信息**：`console.log` 里出现证件号，等于写进了云函数日志，日志保留期比数据库还长

#### 存储方案

| 项 | 做法 |
|---|---|
| 加密算法 | AES-256-GCM（Node 内置 `crypto`，不需要额外依赖） |
| 存储格式 | `v1.<iv>.<authTag>.<ciphertext>`，全 base64；`v1` 是版本号，将来换密钥可平滑迁移 |
| 密钥 | 云函数**环境变量** `ID_ENC_KEY`，32 字节随机；不进代码、不进 git、不进数据库 |
| 盐 | 另一份环境变量 `ID_HASH_SALT`，用于算 `idHash`（查重用） |
| 密钥轮换 | 换密钥时新数据用 `v2`，老数据读到 `v1` 自动解密后用 `v2` 重写——所以版本号必须带 |
| 明文留存 | 只有姓名、手机号是明文（投保必需，且管理员要打给本人） |

#### 访问控制

| 场景 | 谁能看 | 看到什么 |
|---|---|---|
| 报名后本人查看 | 本人 | 自己的脱敏证件号 + 状态 |
| 报名名单 | 管理员 | 姓名、手机、`110***********1234` |
| 导出投保名单 | 管理员 | 完整证件号，**一次性解密**，用完即弃 |
| 任何前端页面 | 所有人 | 永远只有脱敏串，客户端代码里不出现解密逻辑 |

#### 留痕与清理

- **导出必留痕**：写 `id_access_log`，记 `operatorId / eventId / 条数 / 时间`；导出前二次确认
- **导出不落盘**：云函数返回数据、前端本地生成文件，不做「云端 CSV 下载链接」——那等于给了一个可被转发的地址
- **到期自动清理**：定时任务在 `purgeAt` 之后把 `idNoEnc` 置空，只留 `idLast4` + 姓名 + 保单号（对账、理赔查询够用）
- **赛事删除时**：`race_insurances` 一并物理删除，不留孤儿

#### 提审注意

隐私协议必须声明「收集身份证号，用于购买活动意外险」，并写清用途、保存期限、不共享第三方。**不声明会被驳回**。

### 11.4 保险产品本身的四个坑（比系统更重要）

1. **险种要覆盖马拉松**：普通意外险常把「高风险运动」列为除外责任，跑步比赛可能不赔。须买含「马拉松/路跑赛事」的产品或赛事责任险。
2. **年龄限制**：多数团险承保 18-65 岁，超龄的人**买不进去**。报名时校验年龄，超龄标 `excluded`，页面说清「需自行购买可承保产品」。
3. **生效时间**：团险通常要求提前 1-3 天投保，所以「投保截止」必须早于比赛日。
4. **保障范围**：是否含猝死、是否含医疗运送、免赔额多少——要经办人和保险经纪确认，并在赛事页写清。

### 11.5 费用与退赛

- 保费通常含在报名费里，如「报名费 30 元，含意外险 5 元」
- **退赛不退保费**（团险投保后不可退），退费规则里要写明
- 已投保后赛事取消：按保险条款处理，系统只记录状态，不掺和

### 11.6 兜底方案

人数太少、团险不达起售份数时，允许把 `insuranceMode` 切成 `self`（自行购买）。**只有这时**才启用「上传保单截图 + 管理员核验」，核验思路照第 10 节。

### 11.7 免责声明

免责只是**降低纠纷概率，不是免责金牌**。文案不写「一切后果自负」这种无效条款，写明：组织方已为参与者投保、参与者应如实告知健康状况、隐瞒病史的责任自负。

## 12. 边界与坑

1. **成员校验三层**：入口跳登录、按钮提示、**云函数再核 `users`**。只做前端等于没做。
2. **身份口径**：`markers.userId` 是 `users._id`，别混 openid（已踩两次）。
3. **时间口径**：云函数跑 UTC，报名截止、跑步窗口、成绩截止判定都要 `+8 小时`，否则清早/深夜的边界会差一天。
4. **满员不落库**：`count(registered) >= capacity` 读时判定，避免并发写状态。
5. **删赛事保留跑马记录**：成绩是个人资产；记录里冗余 `eventName` 才能删后仍显示。
6. **积分不追回**：赛事删除后已发积分保留。
7. **线上成绩与 PB**：默认不计入，记录标「线上」。若要计入，改一处过滤条件即可，但要想清楚刷榜风险。
8. **订阅消息一次性**：报名申请「报名成功」，赛前提醒要单独再申请授权。
9. **互助自动适用**：自办赛在 `race_events` 里，`raceHelp` 不用改就能用（线下拼车尤其需要）。
10. **评价会进统计**：不想污染赛事评分的话，评价聚合按 `source` 分开。
11. **线上赛没有「现场」**：所以二维码签到、现场名单、物资发放这些线下字段在线上必须隐藏，不能只靠置灰——否则界面会很怪。
12. **同一人重复报名**：按 `userId + eventId` 查重。
13. **证件号只在管理员端出现且脱敏**：报名名单默认不显示证件号；只有「投保导出」时临时解密，并留一条导出日志。
14. **别把证件号放进前端能直读的表**：`race_markers`/`users`/`race_records` 现在都被页面直连查询过，权限多是「所有用户可读」。投保信息必须单独建表、只走云函数，否则加密了也白搭。
15. **日志也是泄露面**：`console.log(err)` 打印整个对象就会把证件号带进云函数日志，排查时只打印 `_id`。
16. **超龄/不承保要报名时就拦**：别等投保才发现买不了——那时人已经占了名额、也交了钱。
17. **团险不退保**：退赛退费规则里写清「保险部分不退」，否则一定有人争。
18. **报名截止不能晚于投保截止**：报名还能进、保险却买不了，是最尴尬的空档。建议报名截止 = 投保截止 − 2 天，或报名页直接显示「含保险，截止前提交投保信息」。

## 13. 分期

**MVP-1 线下（先跑通）**
`source` + 自办赛字段 → 赛事管理表单/筛选 → 报名名单（缴费/签到/代报/导出）→ 详情页报名区（**投保信息 + 单独授权勾选**）→ 投保名单导出与保单回填 → 完赛录成绩 → 删除级联 → 积分

**MVP-2 线上（+1 周）**
`mode='online'` 表单分支 → 提交成绩（截图 + 机械校验）→ 审核页 → 成绩榜 → 记录页「线上」标记与 PB 排除

**V2**
候补队列、电子证书/海报、照片墙、批量赛前提醒、分组年龄段排名

## 15. 待确认

1. **线上成绩是否计入 PB**：默认不计（第 14 条决策）。
2. **线上赛收不收费**：默认免费；要收也是线下收、线上勾。
3. **榜单是否分男女/年龄组**：默认只按距离组别排，不分性别年龄。
4. **谁有审核权**：默认只有管理员；要不要给「裁判」这个独立角色（能审成绩、不能改赛事）？
5. **线上赛是否允许跑步机**：默认允许但要在规则里写清，审核时按赛制判。
6. **保险产品由谁落实**：需要经办人确认——险种是否含马拉松、年龄上限、起售份数、能不能按人天投。
7. **保费是否含在报名费里**：默认含，文案写成「报名费 30 元（含意外险 5 元）」。
8. **非大陆证件怎么办**：团险通常要大陆身份证；港澳台/外籍跑友是否允许报名，需要先问保险渠道能否承保。
